Evidence integrity layer

CLE Protocol

CLE Protocol is the civil-rights evidence integrity layer under Campus Evidence Lab: a public standard for canonical records, deterministic hashes, signed snapshot manifests, Merkle inclusion proofs, local verification tools, responsible-use limits, and optional proof adapters.

Principle

Verification first; blockchain is optional

Campus Evidence Lab remains a public-source research archive. CLE Protocol describes the technical layer that lets users verify records, methodology, corrections, packets, and dataset snapshots without trusting the site blindly.

Blockchain is optional. The protocol must work through local files, signed manifests, GitHub releases, and reproducible hashes before any chain adapter is used.

Do not put sensitive incident data on-chain. Optional public proof adapters are for dataset Merkle roots, snapshot manifest hashes, methodology version hashes, correction-log hashes, source-bundle hashes, reviewer attestation hashes, and evidence-packet hashes.

Protocol Architecture

Local verification before chain integration

Canonical Evidence Data Shared schemas and deterministic canonical JSON for records, sources, corrections, packets, snapshots, methodology versions, and release metadata.
Deterministic Hashes Stable record hashes, source-bundle hashes, correction-log hashes, packet hashes, manifest hashes, and full dataset hashes that can be reproduced locally.
Signed Releases Each release should publish a signed manifest with schema version, record count, source count, methodology version, known limits, hashes, timestamp, and archived files.
Merkle Proofs Dataset snapshots should expose a Merkle root and record-level inclusion proofs so a user can prove a record appeared in a specific snapshot.
Evidence Packets Journalist and researcher packets bundle summaries, timelines, source URLs, citations, methodology notes, limitations, correction history, and verification metadata.
Responsible-Use Layer Policy-as-code checks should warn when outputs imply prevalence, ranking, severity, unsupported comparison, or AI-reviewed claims without human-review metadata.
Local Verifier Developer tools should verify manifests, records, packets, and inclusion proofs from local files before relying on any external timestamping or blockchain service.
Proof Adapters Optional adapters can publish or check manifest hashes through Git tags, GitHub releases, timestamping services, IPFS-like content addressing, or a minimal chain registry.

Developer Utility

Target interface for later protocol tooling

cle verify snapshot snapshot-manifest.json
cle verify record evt_2026_0027 --snapshot snapshot.json
cle prove record evt_2026_0027 --snapshot snapshot.json
cle packet build --school "Example University"
cle policy check chart.json
cle snapshot compare latest previous

These commands are a roadmap for the developer platform. They are not required for the first static protocol page, but they define what the protocol should make possible.

Current Proof Prototype

Optional adapter; no token

The Solidity registry is not the core protocol. It is one possible adapter for publishing snapshot hashes after local verification and signed manifests already work.

Contract
SnapshotRegistry.sol
Stores
Snapshot ID, snapshot hash, metadata URI, publisher, and publication timestamp.
Does not store
Private evidence, sensitive incident details, ranking signals, payments, moderation decisions, source text, or token governance.

Use Boundaries

Credibility depends on restraint

  • No token, no token sale, and no token governance.
  • No legal advice or legal conclusions by Campus Evidence Lab.
  • No school rankings, safety scores, severity scores, or prevalence estimates.
  • No private or sensitive evidence on-chain.
  • Local verification must remain useful even if no blockchain adapter is used.
  • AI may assist research drafting, duplicate detection, extraction, and citation formatting; human review controls publication and verification status.

Verification Paths

Use the smallest artifact that answers the question

Verify Current Snapshot Open manifest, archived snapshot, snapshot index, release metadata, CSV, JSON, schemas, and published hashes. Build Evidence Packet Select records and generate a local packet with source URLs, limitations, citation language, and snapshot hash. Review Methodology Inspect source standards, confidence language, correction handling, and responsible-use rules.
